### D-13 — 파견 확정 (2026-08-21) · U1·U2 해소

**결정**: 기관 현장 배치는 **근로자파견**입니다. 노무사 검토를 거쳤고 근로자파견사업
허가를 보유합니다. CARELINK가 파견사업주, 기관이 사용사업주입니다.

도급으로 설계하려던 대안은 접었습니다. 간병 업무는 병동에서 이뤄지고 병원 간호사의
지시가 사실상 불가피한데, 도급을 유지하려면 그 지시 경로를 차단해야 합니다.
실질이 파견인데 도급으로 계약하면 **위장도급**이고, 그때는 파견법 위반에
사용사업주의 직접고용 의무까지 겹칩니다.

**확정으로 열린 것**: 계약 구조, 기관 영업, 현장 지휘 설계.

**확정과 함께 생긴 의무** (전부 구현 완료):

| 근거 | 의무 | 구현 | 되돌리기 |
|---|---|---|---|
| §6 | 2년 초과 파견 금지 | `DISPATCH_LIMIT_DAYS=730` · 생성 차단 · 90/30일 경고 잡 | 어려움 — 스키마 |
| §7 | 파견사업 허가 | 허가번호 없으면 파견 건 생성 불가 | 쉬움 |
| §21 | 차별적 처우 금지 | `EQUAL_TREATMENT` blocking 체크 | 쉬움 |

**2년 한도를 인력×기관 누적으로 센 이유**: 배치 건별로만 세면 6개월씩 끊어
종료·재배치를 반복해 우회할 수 있고, 그 우회가 정확히 파견법이 막으려는 것입니다.
`dispatchDaysUsed()`가 종료된 건까지 합산합니다.

**상수로 둔 이유**: 이 값은 법에서 옵니다. `matching_rules`처럼 테이블에서 읽으면
누군가 늘릴 수 있게 되고, 늘리는 순간 불법이 됩니다 — §5.5(점수 하드코딩 금지)의
의도적 예외입니다.

**여전히 막힌 것**: `DirectEmploymentStrategy.calculatePayout()`은 **U5**가 막고
있습니다. 24시간 간병의 휴게·대기 시간을 근로시간으로 볼지가 정해지지 않았고,
그 판정이 연장·야간 수당을 통째로 바꿉니다.

### D-14 — 파견 계약서에 교체 절차 명시 (2026-08-21)

2년 한도가 오면 인력을 교체하거나 사용사업주가 직접고용해야 합니다.
그 절차가 계약서에 없으면 **한도가 닥쳐서야 협상**하게 되는데, 이미 사람이
현장에 있는 상태의 협상은 불리합니다.

`DISPATCH_REPLACEMENT_PLAN`(필수 서류)과 `DISPATCH_REPLACEMENT_AGREED`
(blocking 컴플라이언스 체크)로 강제합니다. 최소 기재 사항:

```
교체 통보 시점 (D-90 권장) · 인수인계 기간 · 후임 선정 방식
직접고용 전환을 택할 경우의 절차와 비용 부담
```

`dispatch-limit-warning` 잡은 D-90에 `NOTIFY_ORGANIZATION`,
D-30에 `EXECUTE_REPLACEMENT`를 알림에 실어 보냅니다 — 절차가 계약서에 있어도
알려주지 않으면 아무도 시작하지 않습니다.

### D-15 — F-4 간병 업무 잠정 개방 (2026-08-21) · U3

**결정**: F-4(재외동포) × 병원간병을 `PENDING_CONFIRMATION` → `ALLOWED`.
경영 판단이고 1345 문서 회신 전이므로 **`is_provisional = true`** 로 표시했습니다.

55만 명 모수가 걸려 있어 회신을 기다리며 멈추는 비용이 큽니다. 다만 F-4는
단순노무 제한이 있고 간병이 여기 해당하는지가 회색 영역입니다 (docs/06 §4).

**되돌릴 때를 위해 함께 만든 것** — 이것이 잠정 판정을 운영 가능하게 하는 근거입니다:

| 무엇 | 왜 |
|---|---|
| `visa_eligibility_decisions` (append-only) | `track_visa_eligibility`는 UPDATE로 덮이므로 현재 상태만 남습니다. 이력이 없으면 언제 왜 바뀌었는지 되짚을 수 없습니다 |
| `.../impact` 조회 | 뒤집으면 이미 배치된 F-4 인력이 그 순간 불법 취업이 됩니다. **명단이 몇 분 안에 나와야** 대응이 됩니다 — 배치 중인 인력이 먼저 정렬됩니다 |
| `PATCH .../visa-eligibility/{visa}` | 운영자가 화면에서 바꿉니다. DB를 직접 만지면 이력이 안 남습니다 |

**검증**: ALLOWED에서 F-4 후보 2명이 매칭 통과(score 52) → NOT_ALLOWED로 되돌리자
같은 후보가 `VISA_ELIGIBILITY / visa.eligibility.NOT_ALLOWED`로 제외 → 이력 1건 적재.

**이 결정은 §6-1·§6-11을 어기지 않습니다.** 시스템이 판정한 것이 아니라 사람이
판정한 결과를 데이터로 기록한 것이고, 그것이 `track_visa_eligibility`의 설계 의도입니다.

| **F-14** | SCR-110 탈퇴가 **백엔드에 없음** | `data-retention-purge` 구현 | `DELETE /users/{id}`가 사양에 있는데 구현이 없었음. `UserService.changeStatus`는 있으나 **호출하는 컨트롤러가 없어** 상태머신의 `WITHDRAWAL_REQUESTED` 전이가 도달 불가. 앱 마이페이지의 탈퇴가 동작할 수 없었음 | `DELETE /users/{id}` + `POST /users/{id}/restore`. 본인만 가능 |

## 3. 사양과 어긋나 판단이 필요한 것

**사람이 결정해야 합니다.** 임의로 가정하지 않고 보수적으로 구현한 뒤 올려 둡니다.

### C5 — SCR-502 국적 필터 (README §4에도 기록)

`SCREENS`의 SCR-502는 `GET /admin/candidates?…&nationality=`를 적고 있습니다.
그런데 §5.10은 국적을 "통계·행정 목적에만" 허용하고 §6-13은 "매칭 로직·**필터**·점수"에
금지합니다. 관리 목록 필터가 어느 쪽인지 문언이 갈립니다.

**보수적으로 구현했습니다** — 필터를 만들지 않고 국적은 `admin` scope 표시 필드로만
남겼습니다. 조회 경로가 한번 열리면 그것이 운영 관행이 되고, 관행이 된 뒤에 되돌리는
것은 코드 수정이 아니라 조직 문제가 됩니다. 필요하다고 판정되면 그때 엽니다.

### C6 — 다국어 라벨 확장률이 사양보다 큼 (신규)

SCR-110 notes는 "한국어 기준 길이의 **2.5배**를 수용하도록 설계하세요"라고 합니다.
실측 결과 **최대 4.1배**입니다.

```
journey.visa(ru)            ×4.1   '체류자격 절차' → 'Оформление статуса пребывания'
home.recommended(ru)        ×4.0   '추천 일자리'   → 'Рекомендованные вакансии'
journey.title(vi)           ×3.7   '커리어 여정'   → 'Hành trình nghề nghiệp'
jobs.salary.afterMatch(vi)  ×3.6
journey.title(ru)           ×3.5
```

번역을 줄여서 2.5배에 맞출 수는 있지만 그러면 문구가 어색해집니다.
**설계 기준을 4.5배로 올리는 쪽을 권합니다.** 현재 구현은 고정폭 위젯을 쓰지 않고
`Flexible`/줄바꿈을 허용해 이미 4.1배를 수용합니다. 문서 수정 여부만 판단하면 됩니다.

### C3 — SCR-304 간병사 국적 노출 → **2026-08-21 확정: 노출하지 않음**

시안은 간병사 카드 3장 전부에 `경력 3년 2개월 · 베트남` 형태로 국적을 넣었습니다.
`docs/07` §2.2는 문언상 **'기관' 노출 화면**만 금지하고 SCR-304는 환자·보호자 화면이라
회색 영역이었습니다.

**노출하지 않는 것으로 확정됐습니다.** 보호자가 국적으로 간병사를 고르기 시작하면
그것이 배정 관행이 되고, 검증을 통과한 인력이 국적 때문에 선택받지 못합니다.
플랫폼이 거르는 것은 국적이 아니라 검증되지 않은 인력입니다 (§5.10).

`CLAUDE.md` §6-21에 코드 리뷰 반려 항목으로 올렸습니다. `care` 모듈(V2)의 SCR-304는
카드에 **경력·자격·평점**만 노출합니다.

### C7 — 휴게시간이 야간에 걸렸을 때 야간근로 과다 계상 (신규)

휴게를 **언제** 썼는지는 기록이 없습니다. 그래서 야간(22:00~06:00) 분은 근무 전
구간에서 세고, 휴게를 빼지 않습니다. 야간 교대에서 휴게가 야간대에 걸렸다면
그만큼 야간근로가 많게 잡힙니다 (2교대 90분이면 최대 1.5시간).

휴게 시각을 추측해서 빼는 선택지도 있었지만 하지 않았습니다 — 추측한 값으로
가산수당이 계산되면 틀렸을 때 근거가 없습니다. 지금은 사람이 `correct()`로
정정하고 정정 이력이 남습니다.

**판단이 필요한 것**: 휴게 시각을 기록하게 할 것인가. 간병사가 휴게 시작·종료를
찍게 하면 정확해지지만 현장에서 지켜지지 않을 가능성이 높고, 안 찍으면 휴게를
쓰지 않은 것으로 처리할지가 다시 문제가 됩니다.

### 여전히 열려 있는 것

- **U5** — 24시간 상주의 휴게·대기 시간 판정 → `H24_LIVE_IN` 배정은 집계 자체가 막혀 있습니다
- **U1·U2** — 2026-08-21 해소 (D-13). 남은 것은 `DirectEmploymentStrategy` 급여 계산이며 U5에 걸려 있습니다
- **QR 토큰에 서명·만료가 없음** — 현재 `{hospital_id}:{ward}` 평문 비교입니다. 토큰을 한 번 본 사람은 병실 밖에서도 체크인할 수 있습니다. 서명·만료를 넣을지, 아니면 QR을 병실에 물리적으로 고정하는 운영으로 감당할지 판단이 필요합니다
- `POST /organizations/{id}/saved-candidates` — 스키마에 `saved_candidates` 테이블 없음. `docs/03`을 고치기 전에는 만들지 않음

## 4. 지키기 위해 코드로 강제한 것

규칙을 문서에만 두면 화면이 20개가 되는 순간 지켜지지 않습니다.
아래는 **어기면 컴파일·테스트가 실패하도록** 만든 것들입니다.

| 규칙 | 강제 방법 |
|---|---|
| 색만으로 상태를 전달하지 않는다 | `StatusPill`이 `label` 없는 생성자를 제공하지 않음 + 위젯 테스트가 아이콘 존재를 확인 |
| 점수 단독 노출 금지 (§5.6) | `MatchReasonList`가 `reasons`를 필수 인자로 받음 |
| next_action은 화면당 1개 | `_NextActionCard`가 `List`를 받지 않음 (단수 전용) |
| FIELD 최소 16px / 48px | `CL.minFontSize`·`CL.minTapTarget` + 위젯 테스트가 실제 렌더 높이를 측정 |
| FIELD에 Micro(10.5px) 없음 | 상수 자체를 두지 않음 — 쓸 수 없는 값은 있으면 언젠가 쓰임 |
| i18n 4개 언어 누락 없음 | 키 집합 동일성 테스트 |
| 권한 밖 필드는 미렌더링 | 타입에서 optional → `?? '—'` 강제 + `Restricted` 컴포넌트 |
| 클리어런스 예외 배치 불가 | 화면에 '강제 배치' 버튼이 없음 + 서비스가 던짐 |
| 배선 끊기면 게이트가 닫힘 | `DenyAllPiiUnlock` 기본 구현 |
| 보호자에게 간병사 국적 비노출 (§6-21) | `CaregiverCard` 타입에 필드가 없음 — 그리려 하면 컴파일 실패. API·타입·화면 세 겹 |
| 간병 카탈로그에 의료행위 없음 (§6-2) | 화면이 상수 배열을 두지 않고 `GET /care-services/catalog`만 씀 |
| 보호자에게 서술형 기록 비노출 | `ServiceLog.memo`가 optional — scope가 자르므로 있다고 가정할 수 없음 |
| `service_logs`·`audit_logs` UPDATE/DELETE 금지 (§5.4) | 앱 레이어가 아니라 **DB 트리거**. psql로도 못 고침 |
| 출퇴근은 QR로만 생성 (§6-3) | 기록 추가 엔드포인트가 `SHIFT_START/END`는 **정정으로만** 받음 |
| 24시간 상주 집계 금지 (U5) | 휴게시간 표에 `H24_LIVE_IN` 항목을 두지 않음 — 값이 없으면 던짐 |
| 야간·근무일은 현지 벽시계 | 오프셋 상수 1개 + 회귀 테스트 3건 |
