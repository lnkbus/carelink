## 2. 고용 모델 — 무엇이 달라지는가

### 2.1 세 모델 비교

| | **직접고용**<br>DIRECT_EMPLOYMENT | **위탁·용역**<br>DELEGATION | **순수중개**<br>BROKERAGE |
|---|---|---|---|
| 인력과의 계약 | 근로계약 (CARELINK가 사용자) | 용역·위탁 계약 | 없음 (기관↔인력 직접) |
| 기관과의 계약 | 도급 또는 근로자공급·파견 계약 | 용역 계약 | 유료직업소개 계약 |
| 돈의 흐름 | 기관 → CARELINK → **급여** → 인력 | 기관 → CARELINK → **용역대가** → 인력 | 기관 → 인력 (직접)<br>기관 → CARELINK (수수료) |
| 원천징수 | 근로소득 간이세액 | 사업소득 3.3% | 해당 없음 |
| 4대보험 | **CARELINK 부담** | 원칙적으로 없음 | 없음 |
| 퇴직금·연차 | **발생** | 없음 | 없음 |
| 근로시간 규제 | **적용** | 원칙적으로 미적용 | 미적용 |
| 사고 시 책임 | **사용자 책임** | 계약에 따름 | 원칙적으로 기관 |
| 필요 인허가 | 근로자공급·파견 관련 검토 필수 | 용역업 | 유료직업소개사업 등록 |
| 매출 인식 | **총액** (인건비 포함) | 총액 | **순액** (수수료만) |
| 인력 통제력 | 높음 (품질·근속 관리 가능) | 중간 | 낮음 |
| 고정비 리스크 | **높음** (배치 공백에도 급여) | 낮음 | 없음 |

### 2.2 직접고용을 택했을 때 실제로 생기는 일

직접고용은 **인력 품질과 근속을 통제할 수 있고, 매출을 총액으로 인식**할 수 있다는 큰 장점이 있습니다. 대신 아래가 따라옵니다.

**① 파견 vs 도급 판단 — 가장 큰 리스크**

CARELINK가 고용한 인력이 병원·요양기관 현장에서 일하면, 그 관계가 **도급인지 근로자파견인지** 판정 대상이 됩니다. 판단 기준은 계약서 제목이 아니라 **실질적인 지휘·명령권이 누구에게 있는가**입니다. 병원 간호사가 직접 업무 지시를 하면 도급이라고 써 놔도 파견으로 판정될 수 있습니다.

- 근로자파견은 **허용 업무가 법으로 제한**되어 있습니다. 해당 직군이 허용 업무에 포함되는지, 의료기관 파견에 별도 제약이 있는지 확인이 필요합니다.
- 불법파견으로 판정되면 **사용사업주(기관)에게 직접고용 의무**가 발생합니다. 기관 입장에서 이는 계약을 끊을 만한 사유이며, 사업 자체를 흔듭니다.
- 근로자공급사업 허가가 필요한 형태인지도 별도 검토 대상입니다.

→ **개발 착수와 무관하게, 노무사·변호사 검토를 최우선으로 진행해야 하는 항목입니다.** 플랫폼 설계로 해결되지 않습니다.

**② 근로시간 — 24시간 간병과 근로기준법의 충돌**

24시간 간병을 직접고용 근로자에게 시키면 근로시간·휴게·연장근로 한도 규정과 정면으로 부딪힙니다. 감시·단속적 근로 승인 등 예외 적용 가능성을 검토해야 하며, 이는 **근무 기록 모델 자체를 바꿉니다**. 그래서 `work_records`에 소정근로·야간·연장·휴일을 **분(minute) 단위로 분리 집계**하도록 설계했습니다.

**③ 고정비 리스크**

배치되지 않은 기간에도 급여가 나갑니다. 중개 모델에는 없던 리스크입니다. → 이것이 **간병과 기관 배치를 같은 인력 풀로 묶는 구조가 사업적으로 중요한 이유**입니다. 유휴 인력을 간병 근무로 돌려 가동률을 유지해야 고정비를 감당할 수 있습니다.

**④ 그래서 직접고용은 전 인력이 아니라 일부여야 합니다**

현실적인 구성은 이렇습니다.

```
핵심 인력 (검증·교육 완료, 근속 기대)     → 직접고용
변동 수요 대응 인력                       → 위탁 또는 중개
초기 실험 · 신규 지역 · 신규 산업          → 중개로 시작
```

이 혼재 상태가 **정상이며, 설계는 이 혼재를 전제로 해야 합니다.**

## 3. 전환 가능하게 만드는 설계

### 3.1 핵심 결정: 고용 모델은 **배치 단위**에 붙는다

```
❌ 전역 설정           config.engagementModel = 'DIRECT'
❌ 조직 단위           organizations.engagement_model
✅ 배치 단위           engagements.model          ← 이것
```

이유는 셋입니다.

1. **전환기에 병존해야 합니다.** 기존 배치는 직접고용, 신규는 중개 — 이 상태가 몇 달, 길면 몇 년 갑니다.
2. **지역·트랙·기관별로 달라집니다.** 수도권 요양은 직접고용, 지방 농업은 중개가 합리적일 수 있습니다.
3. **전역 플래그로 두면 전환 시점에 모든 정산 이력이 깨집니다.** 과거 건은 과거 모델로 계산되어야 합니다.

### 3.2 전환은 UPDATE가 아니라 신규 생성

```sql
-- ❌ 하지 말 것
UPDATE engagements SET model = 'BROKERAGE' WHERE id = ...;

-- ✅ 새 engagement를 만들고 previous_engagement_id로 연결
INSERT INTO engagements (..., model, previous_engagement_id) VALUES (..., 'BROKERAGE', <old_id>);
UPDATE engagements SET status = 'ENDED', ended_on = ... WHERE id = <old_id>;
```

과거 근무 기록과 급여 이력은 그 시점의 모델에 묶여 있어야 합니다. 실제로도 근로계약 종료와 새 계약 체결이라는 **법적 절차가 수반되므로**, 데이터 모델이 현실을 그대로 반영하는 편이 맞습니다.

### 3.3 무엇을 공통으로 두고 무엇을 분기하는가

이 구분이 전환 비용을 결정합니다.

| 영역 | 모델 의존성 | 설계 |
|---|---|---|
| 인력 프로필·검증·교육 | **없음** | 공통 |
| 매칭·배치 | **없음** | 공통 |
| 근무 기록 (`work_records`) | **없음** | 공통 — 모든 모델이 같은 원장을 씀 |
| **기관 청구** (`billing_lines`) | **없음** | 공통 — 기관에 얼마 받는지는 모델과 무관 |
| **인력 지급** (`payout_lines`) | **있음** | 모델별 분기 |
| 계약 서류 | **있음** | 모델별 분기 |
| 세무 처리 | **있음** | 모델별 분기 |
| 컴플라이언스 체크 | **있음** | 모델별 분기 |

> **핵심 통찰: 기관에 청구하는 금액 계산은 고용 모델과 무관합니다.** 달라지는 것은 그 돈이 인력에게 어떤 명목으로 나가느냐뿐입니다. 이 경계를 지키면 전환 비용이 정산 모듈 일부로 국한됩니다.

### 3.4 Strategy 인터페이스

```ts
// apps/api/src/modules/engagement/strategy/engagement.strategy.ts

export interface EngagementStrategy {
  readonly model: EngagementModel;

  /** 계약 체결 시 필요한 서류 목록 */
  requiredContractDocuments(): DocumentSpec[];

  /** 배치 전 통과해야 하는 컴플라이언스 체크 */
  complianceChecks(): ComplianceCheck[];

  /** 근무 기록 → 인력 지급액. BROKERAGE는 빈 배열을 반환한다. */
  calculatePayout(records: WorkRecord[], ctx: EngagementContext): PayoutLine[];

  /** 세무 처리 구분 */
  taxTreatment(): TaxTreatment;   // WAGE_INCOME | BUSINESS_INCOME | NONE

  /** 이 모델에서 플랫폼이 수취하는 수익의 형태 */
  revenueRecognition(): 'GROSS' | 'NET';
}

// 구현체
DirectEmploymentStrategy   // 급여대장 생성, 4대보험, 근로시간 검증
DelegationStrategy         // 용역대가, 사업소득 3.3% 원천징수
BrokerageStrategy          // payout 없음, 수수료 라인만
```

**나머지 코드는 이 인터페이스만 알면 됩니다.** `if (model === 'DIRECT')` 분기를 서비스 로직 여기저기에 흩뿌리는 순간 전환 가능성이 사라집니다.

### 3.5 전환 절차 (설계가 아니라 운영 관점)

| 단계 | 할 일 | 시스템에서 |
|---|---|---|
| 1 | 신규 배치부터 새 모델 적용 | `engagements.model` 기본값 변경 (기관·트랙별 설정) |
| 2 | 기존 배치는 계약 만료까지 유지 | 아무것도 안 함 |
| 3 | 만료 시 신규 engagement 생성 | `previous_engagement_id`로 연결 |
| 4 | 과거 정산 조회 | 각 engagement의 모델로 계산된 이력 그대로 |

**시스템 전환에 다운타임이 없습니다.** 이것이 배치 단위 설계의 실질적 이득입니다.

## 4. 3개 트랙 동시 운영

### 4.1 솔직한 우려와, 그럼에도 가능한 이유

앞서 트랙 하나로 좁히길 권했던 이유는 검증 신호가 섞이기 때문이었습니다. 그런데 이번 결정에는 이를 상쇄하는 조건이 있습니다.

**세 트랙이 같은 고객을 공유합니다.** 요양보호·의료지원·병원간병 모두 수요처가 병원과 요양기관입니다. 세일즈 채널이 하나이고, 화면도 하나이며, 기관 입장에서는 "필요한 사람을 한 곳에서 구한다"가 오히려 강점입니다. 트랙별 차이를 **데이터로 빼면** 개발 비용의 증가는 크지 않습니다.

**다만 트랙마다 실제로 다른 것이 있습니다.**

| 트랙 | 자격 경로 | 공급 난이도 | 규제 노출 |
|---|---|---|---|
| HOSPITAL_CAREGIVER | 무자격 가능 + 필수교육 | 낮음 | 업무범위(의료행위) 제한 |
| CARE_WORKER | 요양보호사 자격 (교육기관 이수 + 시험) | 중간 | 자격 요건 |
| HEALTHCARE_ASSISTANT | **국가시험 + 학원 과정** — 리드타임 최장 | **높음** | 자격·의료 관련 규제 |

`HEALTHCARE_ASSISTANT`는 자격 취득까지의 리드타임이 압도적으로 깁니다. 이 트랙만으로 MVP를 검증하려 하면 6개월 안에 공급이 나오지 않습니다.

### 4.2 그래서 이렇게 막습니다

1. **공급 확보는 `HOSPITAL_CAREGIVER`부터.** 무자격 진입이 가능해 가장 빨리 공급이 나오고, 그 근무 기록이 다른 트랙으로 가는 검증된 경력이 됩니다.
2. **KPI를 트랙별로 분리 측정.** 등록 수·검증 완료율·평균 충원 기간을 트랙 단위로 쪼개 대시보드에 표시합니다(SCR-501 수정). 합산 지표만 보면 어느 트랙이 통했는지 영영 모릅니다.
3. **트랙 요구사항은 코드가 아니라 `track_requirements` 테이블.** 트랙이 늘어도 화면과 로직은 그대로입니다.
4. **`HEALTHCARE_ASSISTANT`는 자격 경로 관리에 집중.** 매칭 성사보다 "자격 취득 파이프라인이 굴러가는가"를 지표로 삼습니다. 성과가 나오는 시점 자체가 다릅니다.

## 5. 버티컬 확장 — 농업 · 미용 · 요리

### 5.1 무엇이 같고 무엇이 다른가

**같은 것 (재사용 가능 — 플랫폼의 자산)**

인력 프로필 · 서류 검증 · 교육 이력 · 커리어 여정 · 매칭 엔진 · 기관 관리 · 배치 · 근무 기록 · 고용 모델 · 정산 · 사건 관리

**다른 것 (버티컬마다 새로 정의)**

| 축 | CARE | AGRICULTURE | BEAUTY | FOOD_SERVICE |
|---|---|---|---|---|
| 고객 유형 | 병원·요양기관 | 농가·영농법인·지자체 | 미용실·프랜차이즈 | 음식점·호텔·급식업체 |
| 자격 | 요양보호사·간호조무사 등 | 대체로 무자격 | **국가 면허 필수** | 조리사 면허·경력 |
| 체류·비자 축 | 고용허가제 등 | **계절근로 포함, 지자체 주관 경로 존재** | 제약 큼 | 전문인력·일반고용 혼재 |
| 근무 형태 | 교대·24시간 | **계절성 극심** | 상근·수습 | 교대·주말 집중 |
| 근로시간 규제 | 감시·단속적 근로 검토 필요 | **농림업 적용 예외 여부 확인 필요** | 일반 | 일반 |
| 사업장 규모 | 중대형 | 영세·다수 | **영세·초다수** | 혼재 |
| 전용 서비스 모듈 | **간병 서비스** | 계절 배치·숙소 관리 | — | — |

> 위 표의 자격·비자·근로시간 항목은 모두 **행정사·노무사 확인이 필요한 사항**입니다. 시스템은 이 값을 판정하지 않고, 사람이 판정한 결과를 기록만 합니다.

### 5.2 확장을 가능하게 하는 두 가지 구조 변경

**변경 1 — `career_track` ENUM을 테이블로**

```
industries (산업)
    └── tracks (트랙)
            ├── track_requirements     필요 서류·교육·자격
            └── track_matching_weights 트랙별 매칭 가중치
```

농업 트랙을 추가할 때 **코드 배포 없이 행 추가만으로** 됩니다. ENUM으로 두면 산업이 늘 때마다 마이그레이션과 배포가 필요합니다.

`organization_types`도 같은 이유로 테이블로 바꿉니다. 농가와 미용실은 병원과 다른 유형입니다.

**변경 2 — 플랫폼을 두 레이어로 분리**

```
┌──────────────────────────────────────────────────────┐
│  WORKFORCE CORE  (산업 중립)                          │
│  iam · talent · tracks · org · matching              │
│  engagement · work-record · billing · ops            │
└──────────────────────────────────────────────────────┘
                        ▲
        ┌───────────────┼───────────────┬──────────────┐
        │               │               │              │
┌───────────────┐ ┌───────────┐ ┌───────────┐ ┌───────────┐
│ CARE VERTICAL │ │AGRICULTURE│ │  BEAUTY   │ │FOOD_SERVICE│
│ 간병 요청·배정 │ │계절배치·숙소│ │    —      │ │     —     │
│ 간병사 일정    │ │           │ │           │ │           │
│ 서비스 기록    │ │  (V4+)    │ │  (V4+)    │ │  (V4+)    │
└───────────────┘ └───────────┘ └───────────┘ └───────────┘
```

**`care` 모듈은 버티컬 전용입니다.** 간병 요청·배정·간병사 일정은 다른 산업에 존재하지 않는 개념입니다. 이것을 코어에 섞으면 농업을 붙일 때 전면 재작업이 됩니다.

반대로 **`engagement`, `work_records`, `billing_lines`는 반드시 코어에 있어야 합니다.** 어느 산업이든 사람은 고용되고, 일하고, 정산되기 때문입니다.

### 5.3 확장 순서에 대한 의견

산업을 고를 때 기준은 시장 규모가 아니라 **기존 자산의 재사용률**입니다.

| 후보 | 재사용률 | 진입 난이도 | 의견 |
|---|---|---|---|
| **요리 (FOOD_SERVICE)** | 높음 | 중간 | 교육·자격 경로 구조가 돌봄과 유사. 외국인 인력 수요 큼. **다음 후보로 가장 자연스러움** |
| **농업 (AGRICULTURE)** | 중간 | 중간 | 계절성과 지자체 경로가 코어에 없는 개념을 요구. 숙소·이동 관리 모듈 추가 필요 |
| **미용 (BEAUTY)** | 낮음 | 높음 | 국가 면허 필수 + 사업장이 영세·초다수라 B2B 세일즈 구조가 완전히 다름. **가장 나중** |

다만 이는 현재 정보 기준 판단이며, 실제 순서는 **어느 산업에서 파일럿 고객이 먼저 나오느냐**로 결정하는 편이 낫습니다. 구조는 어느 쪽이 먼저 와도 받을 수 있게 만들어 두었습니다.

### 5.4 새 산업을 추가할 때의 체크리스트

```
□ industries 행 추가
□ tracks 행 추가 (자격 유형, 비자 유형)
□ track_requirements 정의 (서류·교육·자격)
□ track_matching_weights 정의 (기본값과 다른 경우만)
□ organization_types 행 추가
□ 근로시간 규제 적용 여부 확인 → work_records 집계 규칙 검토
□ 비자·체류 경로 확인 (행정사 검토)
□ 자격·면허 요건 확인
□ 해당 산업 전용 모듈이 필요한가? (필요하면 버티컬 모듈로 분리, 코어 오염 금지)
□ 교육 파트너 확보
```

**코드 변경 없이 위 체크리스트만으로 새 산업이 열리는 것이 이 설계의 목표입니다.** 전용 모듈이 필요한 경우에만 개발이 발생합니다.

직접고용 결정으로 새로 열린 항목입니다. 개발보다 **법무·노무 검토가 선행**되어야 합니다.
