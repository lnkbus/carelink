# CARELINK — 정보구조(IA) 및 디자인 시스템

> 화면 사양은 `wireframe/index.html`의 `SCREENS` 배열이 원본입니다.
> 이 문서는 그 41개 화면을 **어떤 구조로 묶고, 어떤 원칙으로 그릴 것인가**를 정의합니다.
> 고충실도 시안 작업(Claude Design)에 들어가기 전에 확정해야 하는 내용입니다.

---

## 1. 이 프로젝트의 진짜 UX 난제

화면 수가 아니라 **사용자 간 격차**입니다.

| 사용자 | 연령대 | 디지털 리터러시 | 언어 | 사용 환경 |
|---|---|---|---|---|
| Candidate | 20~50대 | 중~상 | ko/vi/ru/en | 개인 스마트폰, 여유 있음 |
| **Caregiver** | **40~65세** | **하** | **ko/ru/vi** | **병실, 한 손, 급함** |
| Patient/Family | 40~70대 | 중 | ko | 병원 대기실, 처음 방문, 급함 |
| Organization | 30~50대 | 중~상 | ko | PC, 업무 시간, 반복 사용 |
| Admin | 20~40대 | 상 | ko | PC, 종일 사용, 대량 처리 |

**Caregiver와 Admin을 같은 디자인 시스템으로 만들 수 없습니다.** 억지로 통일하면 한쪽은 못 쓰고 한쪽은 답답합니다.

### 결론: 두 개의 디자인 트랙

```
┌─ FIELD 트랙 ────────────────────────────────────────┐
│  Candidate App · Caregiver App · Patient Web        │
│  원칙: 한 화면 한 과업 · 큰 글씨 · 큰 버튼 · 다국어  │
│  본문 16px+ / 터치 타깃 48px+ / 화면당 주요 액션 1개  │
└─────────────────────────────────────────────────────┘

┌─ DESK 트랙 ─────────────────────────────────────────┐
│  Organization Web · Admin Console                   │
│  원칙: 정보 밀도 · 표 중심 · 일괄 처리 · 키보드      │
│  본문 14px / 행 높이 36~40px / 한 화면 다중 액션     │
└─────────────────────────────────────────────────────┘
```

토큰은 공유하고 **스케일과 밀도만 분리**합니다. 색·타이포 패밀리·아이콘은 하나로 갑니다.

## 2. 앱 구조

### 2.1 클라이언트 구성

| 앱 | 플랫폼 | 트랙 | Phase | 화면 |
|---|---|---|---|---|
| Candidate App | Flutter (모바일) | FIELD | **V1** | SCR-101~110 |
| Organization Web | Next.js | DESK | **V1** | SCR-201~205 |
| Admin Console | Next.js | DESK | **V1** | SCR-501~511 |
| Patient Web | Next.js (반응형) | FIELD | V2 | SCR-301~307 |
| Caregiver App | Flutter (모바일) | FIELD | V2 | SCR-401~405 |
| Partner Portal | Next.js | DESK | V3 | — |

**V1은 3개만 만듭니다.** 환자·보호자는 반응형 웹으로 검증한 뒤 앱으로 확장합니다.

### 2.2 공통 진입 흐름

```
Splash (SCR-001)
   ├─ 토큰 유효 → 마지막 사용 역할로 복귀
   └─ 무효 → Login (SCR-002)
                └─ 역할 0개 → Role Select (SCR-003)
                    역할 1개 → 해당 홈
                    역할 2개+ → 역할 스위처 노출
```

**한 계정이 복수 역할을 가질 수 있으므로 앱 안에 역할 스위처가 필요합니다.** 요양보호사가 간병사를 겸하는 경우가 실제로 흔합니다.

```

   ├─ 진행률 카드
   ├─ 다음 할 일 (단 하나만)
   └─ 추천 일자리 3건

🧭 여정 (SCR-102)
   ├─ 단계별 진행 상황
   ├─ 서류 (SCR-105)
   ├─ 교육 (SCR-106)
   └─ 커리어 트랙 (SCR-103)

💼 일자리 (SCR-107)
   ├─ 일자리 상세 (SCR-108)
   └─ 지원 현황 (SCR-109)

👤 내 정보 (SCR-110)
   ├─ 프로필 (SCR-104)
   ├─ 알림 설정
   ├─ 언어 (ko/vi/ru/en)
   ├─ 상담
   └─ 동의 내역
```

> **탭 4개를 넘기지 마세요.** 다국어 라벨은 한국어보다 길어집니다 ("여정" → "Hành trình" → "Путь"). 5개가 되면 베트남어·러시아어에서 줄바꿈이 납니다.

```
📅 오늘 (SCR-401)   ← 기본 진입. 오늘 할 일 하나 + 큰 버튼 하나
```

**FIELD 트랙에서 가장 보수적으로 설계할 화면입니다.** 40~65세, 한국어가 모국어가 아닐 수 있고, 병실에서 한 손으로, 급하게 씁니다.

## 4. 디자인 원칙

### 4.1 공통 5원칙

| # | 원칙 | 구체 |
|---|---|---|
| 1 | **상태가 곧 UI다** | 모든 상태머신 값에 대응하는 시각 상태를 정의. `PENDING_CONFIRMATION`처럼 "사람이 봐야 하는" 상태는 시각적으로 튀어야 함 |
| 2 | **차단은 이유와 함께** | 매칭 제외·배정 차단 시 반드시 사유 노출. "왜 안 되는지"를 모르면 운영자가 우회로를 찾음 |
| 3 | **점수보다 근거** | 매치 점수는 근거·부족 항목과 항상 함께 |
| 4 | **최소 노출** | 권한 밖 필드는 회색 처리가 아니라 **아예 렌더링하지 않음** |
| 5 | **만료는 카운트다운으로** | 체류자격·클리어런스·서류는 "D-42" 형태로. 날짜만 보면 인지되지 않음 |

### 4.2 FIELD 트랙 추가 원칙

- **한 화면 한 과업.** 홈에 할 일을 나열하지 말고 `next_action` 하나만.
- **본문 16px 이상, 터치 타깃 48px 이상.**
- **글자만으로 상태를 전달하지 않기.** 색 + 아이콘 + 텍스트 3중.
- **입력 최소화.** 자유 입력보다 선택지. 키보드를 띄우는 순간 이탈합니다.
- **오프라인 대응.** 병원 지하·구형 단말. 근무 기록은 로컬 큐 → 재동기화.

### 4.3 DESK 트랙 추가 원칙

- **표가 기본 단위.** 카드 그리드보다 정렬·필터 가능한 표.
- **일괄 처리 필수.** 후보자 100명 단위로 상태 변경·담당자 배정.
- **한 화면에서 판단 완결.** 상세를 보려고 페이지를 떠나지 않게 (드로어/패널).
- **키보드 지원.** 검색 `/`, 저장 `⌘S`, 다음 항목 `J/K`.

### 5.2 타이포

> **보강:** 아래 2열 표에 더해, 시안은 Caregiver·Patient용 **상향 스케일**을 추가로 확정했습니다
> (Display 28/700 · Title 24/700 · Subtitle 19~20/700 · Body 18/400 · Caption 15~16/400).
> 40~65세 사용자가 병실에서 한 손으로 쓰는 화면이라 FIELD 기본 스케일보다 한 단계 큽니다.
> 상세는 `design/README.md`의 타이포 표.

```
sans:  Pretendard  (ko 최적, 라틴·키릴 커버)
mono:  JetBrains Mono 또는 시스템 모노  (ID·코드·시각·금액)
```

**모노를 ID·시각·금액에 쓰는 것이 이 시스템의 시각적 서명입니다.** `#102`, `09:00~17:00`, `₩1,240,000`이 본문과 구분되면 스캔 속도가 확연히 달라집니다.

| 스케일 | DESK | FIELD |
|---|---|---|
| Display | 24 / 700 | 26 / 700 |
| Title | 19 / 600 | 20 / 600 |
| Subtitle | 15 / 600 | 17 / 600 |
| **Body** | **14 / 400** | **16 / 400** |
| Caption | 12 / 400 | 14 / 400 |
| Micro | 10.5 / 500 (라벨) | 사용 안 함 |

**FIELD 트랙에는 Micro 스케일이 없습니다.** 12px 미만은 고령 사용자에게 존재하지 않는 텍스트입니다.

## 6. 다국어 — 4개 언어

**러시아어를 추가합니다.** 고려인 세그먼트(C·E)를 공급 전략에 넣은 이상 필수입니다.

| 코드 | 언어 | 대상 세그먼트 |
|---|---|---|
| `ko` | 한국어 | 전체 · 기본 |
| `vi` | Tiếng Việt | D · F (베트남) |
| **`ru`** | **Русский** | **C · E (고려인)** |
| `en` | English | 예비 |

### 6.1 레이아웃 영향

```
"여정"       2자
"Hành trình" 10자   ← 5배
"Путь"       4자
```

- 탭 라벨·버튼은 **한국어 기준 길이의 2.5배**를 수용하도록 설계
- 고정 폭 버튼 금지. 최소 폭 + 확장
- 줄바꿈 허용. 말줄임(`…`)으로 처리하면 의미가 사라짐
- 숫자·날짜·통화는 로케일 포맷 적용

### 6.2 적용 범위

- **FIELD 트랙: 4개 언어 전부**
- **DESK 트랙: 한국어만** (기관 담당자·운영자는 한국어 사용자)
- 알림은 수신자의 `users.locale`을 따름 → `notification_templates(code, locale, channel)`

**신규 5개가 이 제품의 고유 컴포넌트입니다.** Claude Design 작업 시 이 다섯 개를 먼저 확정하세요. 나머지는 일반적인 패턴입니다.

## 8. Claude Design 작업 순서

문서가 아니라 시각적 판단이 필요한 것만 넘깁니다.

```
1주차  디자인 토큰 시각화 + 핵심 컴포넌트 5종 시안
       → ClearanceMatrix, FunnelTable, MatchReasonList,
         ExpiryCountdown, LocaleSwitcher

2주차  FIELD 대표 화면 3종
       → SCR-101 후보자 홈 (다국어 3개 언어 실제 텍스트로)
       → SCR-102 커리어 여정
       → SCR-401 간병사 오늘 (65세 사용자 기준 검증)

3주차  DESK 대표 화면 3종
       → SCR-501 운영 대시보드 (트랙별 지표 밀도)
       → SCR-504 매칭 센터 (근거 + 비자 게이트 구획)
       → SCR-509 품질·안전 게이트

4주차  나머지 화면 확장 + 반응형 검증
```

**대표 화면 6개가 확정되면 나머지 35개는 조합입니다.** 처음부터 41개를 다 그리려 하지 마세요.

### 8.1 Claude Design에 줄 지시 예시

> `docs/09_IA_및_디자인시스템.md`의 토큰과 원칙을 기준으로,
> `wireframe/index.html`의 SCR-101(후보자 홈)을 FIELD 트랙 고충실도 시안으로 만들어줘.
> 본문 16px 이상, 터치 타깃 48px 이상, 다음 할 일 카드는 하나만.
> 한국어·베트남어·러시아어 3개 버전으로 만들어서 레이아웃이 깨지는지 확인할 수 있게.
